### 3.5 H3 — stock_moves for product 33 Nov 2024, classified by direction

```python
from collections import defaultdict
loc = {r['id']: r for r in q("/rest/v1/stock_locations?select=id,name,warehouse_id,location_type")}

rows = q(
  "/rest/v1/stock_moves"
  "?select=id,quantity,uom,from_location_id,to_location_id,move_date,state,origin,picking_ref"
  "&product_id=eq.33"
  "&move_date=gte.2024-11-01&move_date=lt.2024-12-01&limit=5000"
)

def loc_type(lid):
    l = loc.get(lid); return (l or {}).get('location_type') or ''

def direction(r):
    ft, tt = loc_type(r['from_location_id']).lower(), loc_type(r['to_location_id']).lower()
    if 'supplier' in ft or 'vendor' in ft: return 'INCOMING (from supplier)'
    if 'customer' in tt or 'client' in tt:  return 'OUTGOING (to customer)'
    if 'internal' in ft and 'internal' in tt: return 'INTERNAL TRANSFER'
    return f'OTHER ({ft} → {tt})'

buckets = defaultdict(lambda: [0, 0])
for r in rows:
    d = direction(r)
    buckets[d][0] += 1
    buckets[d][1] += (r['quantity'] or 0)

for d, (n, qn) in sorted(buckets.items(), key=lambda x: -x[1][1]):
    print(f"{d}  lines={n}  sum={qn:,.0f}")
```

## 5. Root-cause summary

### 5.1 CONFIRMED BUG — `locked` state excluded

- **File:** [supabase/migrations/20260422000004_rpc_gerencia_backtest_validation.sql](../../supabase/migrations/20260422000004_rpc_gerencia_backtest_validation.sql)
- **Line:** `AND po.state IN ('purchase', 'done')` in the `comprador_po` CTE
- **Impact:** 77% of all POs in the DB (2,512 of 3,253) are silently ignored when aggregating "Humanos compraron." The page's headline numbers, acierto percentages, and monetary deltas are all affected.
- **Fix:** change to `AND po.state IN ('purchase', 'done', 'locked')`. Not pushed yet — awaiting user decision on the larger reconciliation issue below.

### 5.2 UNRESOLVED GAP — Supabase POLs vs SSOT still disagree after bug fix

Even with the `locked` state included, product 33 Nov 2024 sums to 8,395 ordered / 8,316 received — still **42% higher** than SSOT's 5,917 / 5,500.

### 5.3 Other data gaps observed along the way (not blocking this reconciliation)

- **Archived products**: `products.is_active = false` and `products.archived_at IS NOT NULL` counts are both 0 across the entire DB. Either the ingestion filters archived products out, or does not propagate the flag. Historic sales/PO data for archived sibling SKUs is therefore invisible to any of our aggregations. See [_SILO_DEFINITIONS_APR22.md](_SILO_DEFINITIONS_APR22.md) §2 and [AIREFILL_CLAUDE_ONLINE_HANDOVER_APR21.md](AIREFILL_CLAUDE_ONLINE_HANDOVER_APR21.md) §1 for business context.
- **Mixed currencies on purchase line aggregations**: `purchase_order_lines.unit_price` is stored in the PO's native currency (USD for imports, GTQ for locals). Any SUM(qty × unit_price) across mixed currencies silently under-reports. For SKU 77201046 Feb 2025 (the demo cycle) the PO was GTQ, so the Gerencia page's monetary column is correct for that specific demo SKU. For all other cycles where Reyma/imports were paid in USD, the cost column is wrong by ~7.67×.
- **Header-vs-line cost gap on PO-P-0527**: $345K difference between `purchase_orders.total` and the sum of its line-level `quantity × unit_price`. Almost certainly tax/freight/customs on the header. Not a bug in this context, but worth remembering if anyone uses `purchase_orders.total` directly for per-SKU cost attribution.
