feat: reorder point alerts — Pedir HOY / Pedir esta semana on /compras

Two new KPI cards on the Compras command center answer the timing question
the order-plan panel cannot: which SKUs need an order placed today (stock
already at or below ROP) vs. which will breach their reorder point within
the next 7 calendar days.

Formula:
  rop = avg_daily_demand × (lead_time_days + safety_stock_days)
  HOY:          current_stock ≤ rop
  esta semana:  current_stock > rop  AND
                current_stock − avg_daily_demand × 7 ≤ rop

Safety stock days come from the ABC/XYZ cell policy table (AX=3 … CZ=14)
already used across the app. Counts are mutually exclusive. SKUs with
lead_time_days = 0 or avg_daily_demand = 0 are excluded from both (same
eligibility rule as the order-plan panel).

Demand source: revenue_daily (metric=sales, 90-day window before snapshot),
the validated SSOT formula for the 23 demo SKUs and the same signal already
driving order-plan quantities — chosen for blind-test consistency.

Implementation:
- order-plan/route.ts: ROP counters added inside the existing SKU loop.
  No new DB queries. rop_alerts: { order_today, order_this_week } added
  to the JSON response alongside the existing suppliers array.
  The continue guard (skip zero-cost SKUs from qty calc) moved to after
  the ROP block so demand-only SKUs still contribute to alert counts.
- compras/page.tsx: ropAlerts state wired to the existing planData fetch
  (no new network call). Two-card row inserted between the KPI grid and
  the Order Plan panel. Hover tooltips (group-hover:block, same pattern
  as capital-congelado) explain each definition in Spanish.
