Add end-to-end password-recovery flow so users can reset without admin help.

Until now, every Supabase email template we customized (reset password,
invite, magic link, change email) arrived pretty but functionally dead —
clicking the link dropped users on the home page with an unprocessed token
and no form to set a password. The only way back in was a service-role
admin reset. This commit builds the three routes that make those emails
actually work, plus the forgot-password entry point and the middleware +
login plumbing that lets unauthenticated users reach them.

Routes added:

  - /forgot-password                (frontend/src/app/forgot-password/page.tsx)
      Client page with email input. Calls
      supabase.auth.resetPasswordForEmail(email, {
        redirectTo: `${origin}/auth/callback?next=/update-password`
      }).
      Always shows the same generic success message regardless of whether
      the email exists — prevents account enumeration. Supabase's /recover
      endpoint already returns 200 either way; this keeps the UI honest to
      that posture.

  - /auth/callback                  (frontend/src/app/auth/callback/route.ts)
      Server route handler for the PKCE code-exchange flow. Reads `code`
      and `next` from the query, calls exchangeCodeForSession server-side
      (seats the session cookie), then 302s to `next`. `next` is validated
      to be a same-origin relative path (starts with `/` and not `//`) to
      block open-redirect abuse like `?next=https://evil.com`. Missing or
      invalid codes redirect to `/login?error={missing_code,invalid_code}`
      without leaking which case occurred.

  - /update-password                (frontend/src/app/update-password/page.tsx)
      Authenticated client page with two password fields. Enforces an
      8-character client-side minimum (Supabase server-side floor stays
      authoritative at 6; this is defense in depth). On success, looks up
      the user's role from user_profiles and redirects via
      getDefaultPage(role) — so a gerencia user lands on
      /gerencia/validacion, superuser on /superuser, etc.

Login page updates                  (frontend/src/app/login/page.tsx):

  - New "¿Olvidaste tu contraseña?" link below the sign-in button.
  - Hydrates callback failure codes from `?error=...` into Spanish
    user-facing messages on mount. Uses window.location directly rather
    than useSearchParams to avoid the Suspense-boundary requirement that
    useSearchParams imposes in Next 14.
  - Adds a supabase.auth.onAuthStateChange listener for PASSWORD_RECOVERY
    and SIGNED_IN. This is the fallback path for Supabase's implicit /
    hash-fragment flow: when the email link returns tokens in
    `#access_token=...` instead of `?code=...`, the browser preserves the
    hash across the middleware's 307 redirect to /login, @supabase/ssr's
    detectSessionInUrl parses it on page mount, and the event fires.
    PASSWORD_RECOVERY → /update-password. SIGNED_IN → /backtest. The PKCE
    flow still uses /auth/callback and bypasses this listener entirely.

Middleware update                   (frontend/src/middleware.ts):

  PUBLIC_ROUTES now includes /forgot-password and /auth/callback. The
  inline comment documents why /update-password is deliberately NOT in
  the allowlist — by the time a user reaches that page, /auth/callback
  has already seated the session, so normal auth gating applies.

Flow covered end to end:

  /login → "¿Olvidaste tu contraseña?" → /forgot-password → submit email
      → Supabase sends the Spanish-styled recovery email (already
         configured in dashboard)
      → user clicks link →
         (PKCE)     /auth/callback?code=xyz&next=/update-password
                    → exchangeCodeForSession → /update-password
         (implicit) /login#access_token=...&type=recovery
                    → detectSessionInUrl → PASSWORD_RECOVERY event
                    → router.replace /update-password
      → new password × 2 → updateUser({ password })
      → redirect to getDefaultPage(role)

Not yet covered (deliberate — scope control):

  - Invite-accept flow. Same /auth/callback plumbing would handle it, but
    the invite email currently has no landing page that prompts for an
    initial password. Follow-up.
  - Magic-link sign-in. Would work via the same SIGNED_IN branch, but no
    UI surfaces this option yet.
  - Change-email confirmation. Needs /auth/callback to accept `type=email`
    and skip the password form. Follow-up.
  - Localhost dev loop. Supabase Redirect URL allowlist currently only
    includes the Vercel prod domain; resetPasswordForEmail calls from
    localhost will have their redirectTo silently replaced with the Site
    URL. Fine — dev work rarely needs the recovery flow.

Mechanical tests (localhost) all green:
  /forgot-password           → 200
  /auth/callback (no code)   → 302 /login?error=missing_code
  /auth/callback?code=bad    → 302 /login?error=invalid_code
  /update-password unauth    → 302 /login  (middleware gate)
